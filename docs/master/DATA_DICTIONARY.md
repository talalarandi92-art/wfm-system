## 0. How to read this dictionary

**Provenance codes** (who writes the value — mark of trust):

| Code | Meaning |
|---|---|
| **E** | Engine-computed — written by the reconciliation engine (`backend/scripts/recon-build.js` → `recon-ingest.js`, or the older `import-roster-master.js`). Re-derived on every rebuild; **never patch these in the data — fix the engine** (RULES §18). |
| **I** | Imported — carried verbatim (or lightly normalized) from a source file: `Desktop/ROSTER/CC Schedule 26.xlsx` (monthly matrix / Shifts / Timing tabs), Odoo fingerprint & permissions/sick/comp exports, Ameyo & Sprinklr login exports. |
| **U** | User-entered — typed or clicked in the app (requests, notes, manual edits, admin config). |
| **S** | System — generated by the backend at write time (UUIDs, timestamps, auth bookkeeping). |
| **D** | Derived at read time — not stored; computed in SQL/service code (listed only where confusion is likely). |

**Status labels**: everything in this file is **Confirmed as-built** unless explicitly tagged
`REC-###` (**Recommended** — an improvement that needs the WFM Director's approval before anyone executes it;
per the standing order, recommendations are never dressed as agreed rules).

**Conventions**
- All operational tables are multi-tenant: `tenant_id uuid NOT NULL`. The live/demo tenant is
  `a0000000-0000-0000-0000-000000000001`.
- `*_min` columns are **minutes from local midnight of the row's date** (integers). A value **> 1440** means
  the moment falls after midnight of the *next* calendar day — used for cross-midnight shifts (a cross-midnight
  shift is owned entirely by its **start** day; RULES §19 ★).
- Dates are `date` columns compared as `work_date::text` in SQL to avoid TZ off-by-one (RULES §15).
- Weeks start **Saturday** (RULES §2); cut-off cycles: full-time 15→14, interns 1→end, Bahrain 25→24.

## 1. THE CRITICAL DISTINCTION — `roster_days` vs `roster_daily` vs `attendance_records`

Three tables describe "an employee's day". They are **never interchangeable** (RULES §11 — "NEVER cross-wire"):

| Table | Grain | Written by | Read by | Nature |
|---|---|---|---|---|
| **`roster_days`** (74 cols) | employee × day | Recon pipeline: `recon-refresh.js` = foundation → `recon-build.js` → `recon-ingest.js`; in-system **Upload & Rebuild** button (`POST /attendance-recon/recon-refresh`, perm `schedule.publish`); historical months by `import-roster-master.js` | **Every** `roster-v2/*` report, HR Matrix, Agent-360, OT & Exceptions, WFH HR report, Schedule-grid overlay, request HC-impact, Custom Report/Dashboard Builders | **THE canonical reconciled truth.** Rich: identity (`person_no`), presence, canonical shift times, tardiness, 3 disjoint OT buckets, HR codes, data-quality flags. |
| **`roster_daily`** (18 cols) | employee × day | Legacy `/attendance-recon/upload` + `/ingest` (engine `recon.engine.ts`) | Legacy `/attendance-recon` `/dashboard`, `/metric`, `/overtime`, `hr-weekly`, `hr-matrix` legacy path only | **THIN legacy path.** `/dashboard` **auto-ingests when count==0** — a known landmine. Kept until the legacy endpoints are retargeted. |
| **`attendance_records`** (27 cols) | employee × day (uuid keys) | Workbook import module; Schedule **editCell/publish** (generated weeks tagged `notes='[generated <week>]'`); demand-engine publish/unpublish | Schedule grid *plan* fallback (future weeks), `/dashboard/summary`, legacy dashboards | **The plan/write side.** ~22.8k rows; **carries FUTURE rows** — always cap date anchors `<= CURRENT_DATE`. The Schedule grid OVERLAYS `roster_days` wherever a corrected cell exists (`source:'roster'|'schedule'`). |

Safety net tables (do not report from them): `roster_days_recon_bak` (refreshed on **every** ingest = undo-last-ingest;
restore = `node recon-ingest.js --restore`), `roster_days_predisaster` (full 15,794-row snapshot from the 2026-07-01
partial-upload incident, RULES §20), `roster_days_bak_20260623`, `roster_days_wfhfix_bak`, `roster_daily_bak_20260623`.

`REC-001` (Recommended): retire `roster_daily` by repointing the legacy `/dashboard`,`/metric`,`/overtime` endpoints at
`roster_days` (already flagged as an open drift, RULES §4/§16). Needs approval + re-validation — number-changing.

## 2. `roster_days` — the canonical reconciled day (74 columns, migration 053 + 054/056/057 + ALTERs)

One row per employee × calendar day. PK behaviour: replaced per date-range by the ingest (DELETE range + INSERT),
never row-updated by reports. **Ingest safety rule** (RULES §20): the ingest deletes **only the date range actually
present in the upload** (min..max of `ingest.json`; `RECON_FROM/TO` env override; refuses to delete with no dated rows).

**the rule belongs in `recon-build.js`, not patched into the data** (RULES §18).

## 5. Identity, users & RBAC

### 5.1 `employee_identity` (22 cols) — the canonical spine (migration 058)
One row per **raw** `employee_no`, mapping to `person_no`. `is_canonical` marks the surviving row of an alias pair;
`alias_of` points at the canonical no. Carries per-person report policy: `expected_hours` (def 9),
`include_tardiness` / `include_overtime` / `include_adherence` / `include_kpi` (all def true — the "record-only"
switchboard), `role_category`, `is_supervisor`, `gender`, `team_leader`, `team_group`, `last_working_date`, `status`.
**All analytics resolve raw ids through this table and aggregate by `person_no`** (the `sc` CTE pattern —
REPORTS_AND_ROSTER_ENGINE.md).

### 5.2 `employees` (22 cols)
`id uuid` (the FK used by users/requests/attendance_records/leave_balances), `employee_no varchar` (business key),
names EN/AR, `gender` enum (female-shift rule input), `function_id`/`team_id`, `employment_type` enum (def
`full_time` — drives the cut-off cycle), `status` enum (def `active` — **this**, not `is_active`, excludes leavers
going forward), `hire_date`/`termination_date`, `direct_manager_id`, `is_supervisor`,
`productivity_factor numeric def 1.00` (intern ≈ 0.70 per capacity rules), `odoo_id` (integration key), `notes`.
`employee_aliases` (migration 005) records merge history from the duplicate-merge tool.

### 5.3 `users` (22 cols) + RBAC
`users`: `email`, `username`, `password_hash` (bcrypt), `employee_id` → employees, `status` enum def `pending`
(self-registration approval flow), lockout fields (`failed_attempts`, `locked_at`, `locked_until`), rotating refresh
token (`refresh_token_hash`/`_expires_at`), `must_change_password def true` (bulk-import temp passwords),
`mfa_secret`/`mfa_enabled` (migration 039), `last_login_at/_ip`.
RBAC: `roles` / `permissions` / `role_permissions` / `user_roles` (+ `revoked_tokens` migration 009,
`role_working_hours`, `tenant_settings`, `tenants`). **Final access model** (migration 040): admin = all;
RTA + TL = admin-minus-settings; agent = own data via `/me`. Sensitive actions gated by permission strings
(e.g. `schedule.publish` guards the recon rebuild).

### 6.3 `leave_balances` (10 cols, migration 038) + `holidays`
`leave_balances` stores **entitlement only** (`employee_id`, `leave_type`, `calendar_year`, `entitlement_days`,
`created_by`); **taken/pending are computed live** from approved/pending `request_leaves` — no denormalized "taken"
column to go stale. Opt-in over-request block. `holidays` (`tenant_id`,`holiday_date`,`name`) is the **editable**
official-holiday table, **mirrored from `backend/scripts/recon-config.json` on every recon-ingest** — edit the config,
rebuild, and both the engine (holiday-OT, leave-on-holiday) and the balance calc agree. All 2026 holidays loaded.
